## Destination

A handoff spec that names every GitHub touchpoint in Code Review Sage and its Bitbucket Cloud equivalent, sufficient for someone to build the port. The build itself is out of scope. Bitbucket Cloud only; Data Center/Server out of scope for V1.

## Notes

Domain: KiroCrew app port, Python backend + external React UI. Tracker: Backlog.md (this repo). Skills each session should consult: grilling + domain-modeling for design decisions. Repo is a clean copy of the GitHub app at /Users/christian.bonzelet/workspace/personal/kiro-crew-apps/bb-code-review-sage. Target Bitbucket repo: workspace dflds, repo content.hub. Transport is decided (see Decisions so far): Atlassian Rovo MCP v2, discover tool names at runtime.

Architecture fact (verified from adapters.py): the review brain only ever sees a normalized ReviewTarget dataclass. Adding a platform is a new adapter + config, not a brain change. GitHub coupling is concentrated in adapters.py (parse+identity), discovery.py (gh plumbing), three dicts in pipeline.py (FETCH_SPECS, POSTING_SPECS, list_open_prs/build_github_review_payload), and the review_driver.py poster/confirm blocks. The learning + store data model is already platform-clean (no GitHub node IDs persisted; repo_identity is a plain host/owner/repo string, change_id a GH- prefix).

## Decisions so far

- [Research: Bitbucket transport via Atlassian Rovo MCP](TASK-1.4): Rovo MCP v2 exposes every op Sage needs (list/get PRs, get diff, list/add comments, create PR task) via discover + executeRead/executeWrite. No App Password / separate REST client needed. Exact tool names vary across Atlassian docs; resolve via `discover` at runtime. Inline anchor keys: path, from (old side), to (new side), start_from/start_to for ranges. Rate limits: authed /2.0/repositories scaled 1000-10000/hr; Rovo site cap 500-10000/hr. (REFINED by TASK-1.5: Bitbucket Cloud DOES have a native `pending` comment field + a Start-review/Finish-review UI batch flow, but NO documented API publish-batch endpoint, and Rovo drives immediate add-comment only — so native staging is not usable through our transport.)
- [Research: PR fetch + discovery + pipeline touchpoints](TASK-1.1): ReviewTarget has 14 fields (adapters.py:42-63). Single-PR fetch is an LLM instruction string (pipeline.py FETCH_SPECS, the worker runs `gh api`), NOT a Python subprocess. Discovery (list_open_prs, list_user_repos) IS deterministic `gh` subprocess. Adapter seam = adapters.py + discovery.py + pipeline dicts. Brain (ReviewTarget, orchestration) stays untouched.
- [Research: review-posting + learning + identity touchpoints](TASK-1.2): Posting = one GitHub PENDING review carrying inline comments + a body, delete-and-recreate dedup by literal marker `[code-review-sage]` in the body, human submits later. Bot identity = whatever gh is authed as (no dedicated account); ownership is body-marker based, so portable. Learning subsystem is platform-clean and ports unchanged. This PENDING model is the port's real work.
- [Research: backend routes + config + app.json + React UI](TASK-1.3): 8 of ~20 routes assume GitHub. Central config key is github_hosts (store.py:87,120). app.json has no config schema/secrets block; declares gh CLI dependency and github tags/prose. UI IS NOT IN THIS REPO — it lives in an external website/ tree (website/src/apps/code-review-sage/CodeReviewSagePage.tsx). Settings API does not expose github_hosts.
- [Decide the Bitbucket posting model](TASK-1.5) — THE KEYSTONE: Chose **Sage-side staged review**. Sage holds the review as an internal draft; a human clicks Publish in Sage's UI; Sage fires a sequential Rovo add-comment loop. Artifact = one marker-bearing summary comment (canonical) + inline comments for Critical/High only. Advisory in V1 (no merge-block). Dedup identity = path+rule+content-hash (line-drift tolerant), embedded as a hidden per-comment marker; re-publish reads existing marker comments and skips/PUT-updates the summary. Native pending staging ruled out of V1 (Rovo can't drive publish-batch). The draft store + publish endpoint fold into TASK-1.7's scope.
- [Research: website/ React UI GitHub touchpoints + where the publish surface lands](TASK-1.9): The UI is a PORT, not net-new — the draft-review + Publish bar ALREADY exists (`components/DraftReviewActions.tsx` → `PrReviewDetail.tsx`, siblings `PostCommentsButton.tsx` + `ShipSummaryCard.tsx`). github.com coupling is narrow: only `Ct()` (`https://github.com/${owner}/${repo}`, feeds `repoPrs`/`reviewRepo`) and the add-PR input regex `github.com/.../pull/N`; display parsers + auth remediation (`gh`/`glab`) are already provider-aware, no Enterprise/pin strings. Posting is NOT fire-and-forget: the UI bakes in GitHub PENDING-review semantics (`pending_only_you_can_see_it_until_you_publish`, irreversibility + `contentDigest` staleness guards, APPROVE/REQUEST_CHANGES/COMMENT verdicts). CRITICAL: the shipping publish bar calls the **platform source layer** `/api/source/pull-request/{pending-review,submit-review}`, while TASK-1.5's Sage-side model is shaped for the **app layer** `/runs/{id}/post` — surfacing a new decision (see TASK-1.10). No `website/` tree exists on this machine; source confirmed in `kirodotdev/KiroCrew@HEAD` via `gh api` + compiled bundle.
- [Spec the Bitbucket PR fetch + ReviewTarget mapping adapter](TASK-1.6): Fetch stays an LLM-instruction (fetch_spec('bitbucket') → discover + getBitbucketRepoPullRequest/…Diff/…Comments), mirroring GitHub's fetch=instruction / parse=deterministic split. New parse_bitbucket_payload maps to the same 14-field ReviewTarget (repo_identity='bitbucket.org/dflds/content.hub', change_id=BB-<ws>-<repo>-<id>, description=summary.raw, author=author.nickname, target_branch=destination.branch.name, revision=source.commit.hash). Biggest new code = a unified-diff splitter for files[] (Bitbucket returns ONE PR-wide diff, no per-file patch array). detect_platform routes on host=='bitbucket.org' + '/pull-requests/' (hyphenated+plural). linked_issue repurposed to Jira keys, else ''. New bitbucket_change_id + bitbucket_review_key mirror the GitHub helpers. NO new ReviewTarget field: inline from/to anchors are derived by the 1.7 poster from files[].diff.
- [Spec the Bitbucket poster + idempotency](TASK-1.7): Platform-neutral `build_review_payload(record, platform)` emits a Bitbucket `{summary, inline}` WORK LIST (one always-present marker-bearing summary comment + inline for 🔴/High only) instead of GitHub's single PENDING-review envelope. Inline `{path, from, to}` anchors derived in Python from finding.line + the 1.6 diff-split `files[].diff` (walk `@@` hunk headers: added line → `to`, else `from`); unanchored findings fold into the summary. IDEMPOTENCY (corrects a map assumption — GitHub's real dedup is NOT marker-delete alone but a durable per-comment ledger `posted_keys` gated by a content read-back `_draft_confirmed`, made atomic by GitHub's one-POST review): Bitbucket loses BOTH atomicity (N sequential posts → ledger updates PER COMMIT) and delete-reset (comments permanent → re-publish reads + skip/PUT-updates). Keep BOTH mechanisms — hidden per-comment marker `[code-review-sage:<path>#<rule>#<hash8>]` (line-drift tolerant, survives store loss) + a durable `published.json` ledger keyed by `bitbucket_review_key` mapping `marker_id → bitbucket_comment_id`; a live `executeRead` read-back (`_posts_confirmed`) is authoritative and reconciles the ledger; delivery evidence is the live comment_id, never the poster's self-count (fail-closed preserved). Rate limits: artifact small by design + ~200-300ms inter-call delay + exp-backoff on 429 then stop. Renames kill the leak: `github_review_payload`→`review_payload`, `build_github_review_payload`→`build_review_payload`, `_draft_confirmed`→`_posts_confirmed`. Names the backend publish-endpoint contract TASK-1.10's UI decision binds to; route wiring is TASK-1.8.
- [Spec the Bitbucket config, identity + discovery model](TASK-1.8): **A2 + C1**. Config: replace the `github_hosts` host-allowlist with `bitbucket_repos: [{workspace, repo}]` in store.DEFAULT_CONFIG (no safe default → unconfigured Sage fails closed); `allowed_hosts()` becomes `allowed_targets()` returning `(workspace, repo)` pairs, and the review_driver.py fail-closed guard revalidates target-in-scope instead of host. Identity: Sage posts as the Rovo MCP token's user (analog of "whatever gh is authed as"); ownership stays marker-based via `[code-review-sage]` — no bot account, no identity port work. Discovery: DROP the personal gh-feed pickers (list_user_repos, list_contributed_repos); keep only list_open_prs rebuilt on Rovo listBitbucketRepoPullRequests scoped to a configured repo (answers 1.6's hand-off: it becomes an MCP call, not a `gh` subprocess); remove /recent-repos + /my-repos routes; /repos CRUD manages the config list. app.json: drop the gh dependency, rewrite github prose, ADD a config schema block for bitbucket_repos (required, no default).
- [Decide the Bitbucket UI publish surface](TASK-1.10) — THE UI KEYSTONE: Chose **Option B** — the Publish bar drives the app layer `/runs/{id}/post`, NOT a faked platform-source `/api/source/pull-request/*`. No Bitbucket source-provider impl is written (source layer stays GitHub-only; Bitbucket bypasses it). `DraftReviewActions` is reworked to call the app layer; staleness guard KEPT but Sage-owned (off ReviewTarget `revision`=source.commit.hash from 1.6, not the source layer's `contentDigest`); irreversibility warning KEPT (truer on Bitbucket — comments are permanent). **Scope change vs 1.5: verdict-driving moves INTO V1** — Approve/Request-changes fire from Sage directly (no web-UI context switch), as discrete buttons SEPARATE from Publish. Confirmed live via Rovo `discover`: `approveBitbucketRepoPullRequest` + `requestChangesOnBitbucketRepoPullRequest`, both executeWrite, args `{workspaceId, repoId, prId}`, no verdict/body field. **Load-bearing constraint:** Rovo has NO un-approve/withdraw op and NO reviewer-status read op → verdicts are one-way from Sage; handling = **confirm-before-fire** (dialog states undo needs the Bitbucket web UI). Graduates the draft-store lifecycle (TASK-1.11) and the component-by-component UI spec (TASK-1.12).
- [Spec the Bitbucket draft-store lifecycle](TASK-1.11): CORRECTS the ticket's premise from code — the result record `data/runs/<id>/results/<cid>.json` ALREADY is the Sage draft, `clear_results()` fires at the NEXT run's START (review_driver.py:1135), NOT at run end, and posted state lives INLINE on the record (no `published.json` today). Five decisions: **(1)** posted state stays INLINE — DROP TASK-1.7's separate `published.json`; store `posted` map `{marker_id → {comment_id, posted_at, revision}}` on the record; the live-comment marker stays only as the record-loss RECOVERY path. **(2)** retain via a `hold_for_publish` flag — `clear_results` skips records where `hold_for_publish=true AND fully_posted=false`; cleared only on all-markers-confirmed (`_posts_confirmed` read-back) or explicit discard; NO TTL. **(3)** persist findings + `revision` at run completion, compute the `{summary,inline}` work list LAZILY on GET/publish (payload is derived, TASK-1.7 rebuilds it each publish). **(4)** pre-publish read = `GET /api/apps/code-review-sage/runs/{id}/draft?change_id=<cid>` → `{change_id, revision, hold_for_publish, findings[], summary, inline[], posted[], stale}`, each item carrying its marker key + `status: new|published`; pure read. **(5)** staleness: store `revision` (from 1.6) at completion, compute `stale` at GET via one Rovo `executeRead` on live PR head, RE-CHECK fail-closed at publish (refuse + tell user to re-run, never post against a moved head).
- [Spec the Bitbucket UI port: components, verdict controls, wire contracts](TASK-1.12): Confirmed against `kirodotdev/KiroCrew@HEAD` — corrects THREE map assumptions. **(A)** No `Ct()` URL builder exists in `lib/format.ts` (that name came from the minified bundle); the github coupling is FOUR regex parsers (`repoOfRun`, `sageSourceLink`, `prLabelFromChange`, `prRefFromChange`) — edit those to accept `bitbucket.org/.../pull-requests/N`. No URL builder to touch (`repoPrs`/`reviewRepo` take an `owner/repo` string, backend builds the URL). **(B)** Two publish paths ship: app-layer `PostCommentsButton`→`/runs/{id}/post` (already the Sage model) AND source-layer `DraftReviewActions`→`api.pullRequestPendingReview`/`submitPullRequestReview` (GitHub-PENDING release bar). On Bitbucket the app-layer post IS the publish, so they COLLAPSE — re-point `DraftReviewActions` at the app layer (draft GET + `/post`), keep preview + irreversibility warning, drop `contentDigest`/`supersededDraft`/`expectedReviewId`/`autoMerge` guards, render new-vs-published off the GET's `status`, disable on `stale`. **(C)** Verdict is a SELECTOR fused into the source-layer submit (one GitHub POST = comments + verdict); on Bitbucket comments and verdict are DIFFERENT endpoints, so split it into a NEW sibling `VerdictActions.tsx` (discrete Approve / Request-changes, confirm-before-fire, "undo needs Bitbucket web UI"), never fused with Publish. `PostCommentsButton`/`ShipSummaryCard` need only prose edits (contract + `postedKeys` already app-layer + Bitbucket-shaped). Wire contracts pinned: draft GET (NEW), `/post` (unchanged + `target_stale`), `/approve` + `/request-changes` (NEW, wrap Rovo executeWrite). `sageSourceLink`→null for Bitbucket is intentional (no source-provider impl per TASK-1.10). **LAST major decision ticket — route wiring for the new endpoints folds into TASK-1.8.**
